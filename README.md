# Ракурс

Кабинет продаж: компания владеет несколькими агентами — ИИ-продавцами, у каждого свои
разделы. Люди входят в компании по приглашению, с ролью владельца или участника.

| Пакет | Что это |
|---|---|
| [`rakurs/`](rakurs/README.md) | фронтенд — React: вход, выбор агента, настройки агента и оболочка разделов |
| `server/` | бэкенд — Fastify, PostgreSQL |
| `packages/contract/` | доменные типы, общие для обоих: контракт не может разъехаться |
| `deploy/` | Compose, nginx, [инструкция по деплою](deploy/README.md) |

## Запуск локально

Нужен Docker. **Все команды ниже — из корня репозитория**, того каталога, где лежит этот
файл. `--prefix` отсчитывается от текущего каталога, поэтому из домашней папки npm пойдёт
искать `~/server/package.json` и не найдёт.

Первый раз:

```bash
npm install
cp server/.env.example server/.env
docker compose -f deploy/compose.dev.yml up -d
DATABASE_URL=postgres://rakurs:rakurs@localhost:55433/rakurs_dev npm --prefix server run migrate
```

Завести компанию и её владельца — экрана регистрации нет, аккаунты заводятся из терминала:

```bash
npm --prefix server run create-account
```

Добавить сотрудника в существующую компанию:

```bash
npm --prefix server run add-member
```

Если человек с такой почтой уже заведён, он просто получит доступ ещё к одной компании:
пароль спрашивается для новых людей и на существующих не влияет.

Дальше два терминала:

```bash
npm --prefix server run dev
```

```bash
npm --prefix rakurs run dev
```

Кабинет на http://localhost:5173, бэкенд на http://localhost:3000. Переменные сервер берёт
из `server/.env` сам, руками ничего передавать не нужно.

База в `compose.dev.yml` лежит на именованном томе, поэтому пользователь и данные переживают
перезапуск контейнера. Тестовая база — отдельная (`compose.test.yml`, порт 55432, tmpfs):
её каждый прогон тестов чистит, и заводить там что-либо бессмысленно.

Для WhatsApp `server/.env` держит пять дополнительных переменных:

- `META_APP_SECRET` — секрет приложения Meta, подписывает каждый вебхук;
- `META_WEBHOOK_VERIFY_TOKEN` — строка, которую Meta присылает при проверке вебхука;
- `CREDENTIALS_KEY` — ключ шифрования токенов в базе, ровно 32 байта в base64, получить:
  `head -c 32 /dev/urandom | base64`;
- `MEDIA_DIR` — куда сохранять файлы из WhatsApp, по умолчанию `var/media`; в продакшене
  `deploy/compose.yml` эту переменную не читает: путь внутри контейнера задан там жёстко,
  чтобы совпадать с именованным томом;
- `PUBLIC_URL` — как сервер виден снаружи, из него собирается адрес вебхука; обязателен,
  сервер не запустится без него, но если он не указывает на публично доступный адрес
  (например, остался `http://localhost:3000` из примера) — кабинет работает, а сообщения
  от Meta не приходят: ей некуда их доставить.

Подробности и подключение номера — в [`docs/whatsapp-setup.md`](docs/whatsapp-setup.md).

## Что уже работает

Вход и выход, компании и агенты, настройки агента — на настоящих данных из PostgreSQL.

WhatsApp подключается через официальный Cloud API: диалоги хранятся и на них отвечают прямо
из кабинета, а реклама, из-под которой пришёл диалог, запоминается для этапа Conversions
API. Как подключить номер — в [`docs/whatsapp-setup.md`](docs/whatsapp-setup.md).

Диалоги собираются в воронку: доска стадий с переносом карточек, карточка лида рядом с
перепиской, заказы с ручной отметкой оплаты и таблица клиентов с выгрузкой в CSV. Стадии и
поля лида настраивает владелец. Как это устроено — в
[`docs/orders-funnel.md`](docs/orders-funnel.md).

База знаний хранит факты, которыми отвечает ИИ-агент: записи заводятся руками, вставкой
текста или импортом страницы сайта, и ищутся тем же поиском, которым пользуется агент. Как
её наполнять — в [`docs/knowledge-base.md`](docs/knowledge-base.md).

ИИ-агент отвечает клиентам в WhatsApp по базе знаний через OpenRouter, двигает лидов по
воронке и передаёт диалог человеку, когда фактов не хватает; проверить его до включения
можно в песочнице. Что он умеет и чего не умеет — в [`docs/ai-agent.md`](docs/ai-agent.md).

Оплаченные заказы уходят обратно в Meta через Conversions API, чтобы реклама искала похожих
покупателей: набор данных подключается в «Интеграциях», журнал показывает, что ушло, а что
нет и почему. Отправляются только диалоги, начавшиеся с клика по рекламе Click-to-WhatsApp.
Как подключить и что уходит о клиенте — в [`docs/meta-capi.md`](docs/meta-capi.md).

Остальные разделы показывают, на каком этапе они появятся. Это ожидаемое состояние, а не
поломка: экран без эндпоинта честно об этом говорит.

| Этап | Что подключает | Состояние |
|---|---|---|
| 1 | Компании, агенты, роли, каркас кабинета | готово |
| 2 | WhatsApp Cloud API: подключение номера, диалоги, вебхук | готово |
| 3 | Заказы: доска стадий, карточка лида, заказы и клиенты | готово |
| 4 | База знаний: записи, импорт страниц, поиск | готово |
| 5 | ИИ-агент: ответы по базе знаний, модели OpenRouter, песочница | готово |
| 6 | Meta Conversions API: покупки обратно в рекламу | готово |
| 7 | Статистика: воронка, конверсия, источники | |

Замысел и решения — в [дизайн-документе этапа 1](docs/superpowers/specs/2026-09-02-tenancy-and-shell-design.md),
план работ — в [плане этапа 1](docs/superpowers/plans/2026-09-02-tenancy-and-shell.md).

Документы с датой 2026-08-06 в тех же каталогах описывают более раннюю модель продукта —
отслеживание продаж по креативам — и оставлены как история.

## Правила, которые легко нарушить

**Ничего секретного с префиксом `VITE_`.** Всё с этим префиксом вкомпилируется в бандл и будет
видно любому, кто откроет исходники страницы. Токены Meta и ключ модели живут только на сервере.

**Контракт правится в `packages/contract/`**, а не в двух местах. Фронт и сервер импортируют
один файл, поэтому расхождение — ошибка компиляции, а не сюрприз в проде.

**Ноль вместо «не знаем» — ошибка.** Если данных нет, ответ содержит `null`, а экран пишет
словами, чего именно нет. Выдуманные цифры и статусы недопустимы: на них принимают решения
о деньгах.
