# Attribution and money

How a WhatsApp conversation gets bound to an ad, how it gets analysed, and how a payment
travels back to Meta. Part of [Rakurs — Production Readiness](2026-08-06-rakurs-production-design.md).

## Binding a conversation to an ad

Baileys speaks the raw WhatsApp protocol. It does **not** receive Meta's click-to-WhatsApp
referral the way the official Cloud API webhook does, so the link between an ad and a
conversation has to be carried in the message text itself.

**Tracking codes.** Rakurs generates a four-character code per ad — Crockford-style base32 with
`0/O` and `1/I/L` removed, so nothing is ambiguous when read off a screen — and stores it in
`ads.tracking_code`. A settings screen lists every ad with its code and the suggested prefilled
text, one copy button per row:

```
Здравствуйте! Интересует [K7XM]
```

The client pastes that into the ad's message template in Ads Manager. Codes are generated by us
rather than parsed out of the ad creative because creative structure differs per ad format in
the Marketing API; a parser would break on every format the client tries next.

**Detection.** On each of the first three inbound messages of a new conversation, match
`\[([A-Z0-9]{3,5})\]` and look the code up in `ads`. Three messages rather than one: clients
sometimes greet first and send the prefilled text second, or edit it before sending.

**Referral, when it shows up.** Some ad formats deliver `contextInfo.externalAdReply` through
Baileys, carrying the source ad directly. When present and resolvable, it wins — it comes from
WhatsApp rather than from text a client could have edited. It is not guaranteed for every
format, so it is a bonus path, not the mechanism.

Precedence: `referral` → `code` → `manual` → unattributed.

**Unattributed is a real state.** No code, no referral, no manual binding leaves
`attribution_source` null, and every screen says "источник не определён". Guessing by arrival
time would silently mis-assign revenue between ads, which is worse than an honest gap.

**Manual binding** is available from the dialog card: pick an ad, set `attribution_source =
'manual'`. Needed for conversations that started before codes were deployed.

## Meta synchronisation

Job `sync_meta`, every 30 minutes:

| Call | Writes |
|---|---|
| `GET /{business_id}/owned_ad_accounts` | `ad_accounts` |
| `GET /act_{id}/ads` — id, name, adset, campaign, effective_status, creative | `ads` |
| `GET /act_{id}/insights` — `level=ad`, `time_increment=1` | `ad_daily` |

Each run refetches the **trailing 7 days**, not just today: Meta restates recent numbers for
days after the fact, and a single-day sync would freeze yesterday's spend at its first,
incomplete value. A nightly job backfills the full 90-day window.

Rate limits are read from the `X-Business-Use-Case-Usage` response header; above 80% usage the
job backs off and reschedules rather than pushing into a throttle.

`PATCH /api/ads/:id` maps to `POST /{ad_id}` with `status=ACTIVE|PAUSED`, then refreshes that
one ad's row. The UI already applies toggles optimistically and rolls back on error.

## Conversation analysis

Triggered by a `analyze_conversation` job scheduled 10 minutes after the last message; a new
message reschedules the pending job rather than queueing a second one. A conversation is
analysed once per state of itself — the job exits immediately if `messages_hash` is unchanged.
`POST /api/dialogs/:id/reanalyze` forces a recompute regardless.

Input: the transcript with speaker roles and timestamps, the seller's name, and the bound ad's
name when there is one. Conversations over 200 messages are sent as head plus tail — truncating
to the most recent messages alone would cut off the request that started everything, which is
exactly what `ask` and `purpose` are asking about.

Output is a strict JSON schema mapped to the `analyses` columns, obtained through structured
output rather than parsing prose, so a malformed response fails loudly instead of writing
half-empty rows. Model: `claude-sonnet-5`, behind an adapter interface — the provider is one
implementation, not a dependency threaded through the codebase.

## Payment import

There is no CRM. The owner pastes free text, and the text contains client phone numbers.

1. `POST /api/payments/import` with the raw text creates a `payment_imports` row in `parsing`
   and enqueues `parse_payments`.
2. The model extracts rows — phone, name, amount, currency, date — into the same kind of strict
   schema used for analysis. Format is deliberately unconstrained: any list the owner already
   keeps should work without reformatting.
3. Phones normalise to E.164, falling back to `DEFAULT_COUNTRY` for numbers written without a
   country code.
4. Matching: exact `contacts.phone_e164` hit → `exact`. Phone unusable but a name matching
   exactly one contact → `fuzzy`. Neither → `none`.
5. The preview table returns to the screen with the matched client, conversation and ad per row.
   Unmatched and fuzzy rows are flagged. The operator edits, discards or accepts each.
6. `POST /api/payments/import/:id/confirm` writes `payments` and enqueues one `send_capi` per row.

**Unmatched payments still count as revenue.** They land in `payments` with a null
`conversation_id`, appear in period totals, and simply do not attribute to an ad. Dropping them
would understate the money the business actually made, which is the one number nobody will
tolerate being wrong.

Re-importing an overlapping list is expected behaviour, not misuse. The unique index on
`(phone_e164, paid_at, amount)` absorbs it.

## Conversions API

One `send_capi` job per confirmed payment, posting to
`POST /{pixel_id}/events`:

```
event_name    Purchase
event_time    payments.paid_at
event_id      capi_events.event_id        — Meta's own deduplication key
action_source business_messaging
messaging_channel whatsapp
user_data.ph  sha256(E.164 without '+', lowercased)
custom_data   { value, currency }
```

Phone hashing happens server-side and the raw number never leaves in a payload. Failures retry
with exponential backoff up to a bounded attempt count, then park as `failed` and surface on the
reconciliation panel rather than retrying forever.

Payments with no bound ad are **still sent**. Meta matches events to people by the hashed phone;
whether Rakurs knew the source ad is irrelevant to the algorithm's training, and withholding
those events would weaken optimisation for no gain.

**One honest limitation.** `Event Match Quality` is not returned per event by the Conversions
API — it lives in Events Manager. The reconciliation panel can show accepted, sent, confirmed,
pending and failed from our own tables, all of which are exact. EMQ has to be entered manually
in settings or left blank; the screen must not invent a number for it.
