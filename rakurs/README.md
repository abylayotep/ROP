# Ракурс

Кабинет отслеживания продаж по креативам: показывает, какая реклама приносит **деньги**,
а не заявки, и где эти деньги теряются в переписке продавцов.

Ключевая механика, вокруг которой построен весь интерфейс: оплаты из CRM уходят обратно
в Meta через Conversions API с суммой чека. Поэтому алгоритм оптимизируется на покупателей,
а отчёты показывают реальный ROAS по каждому объявлению.

**В приложении нет ни одной зашитой цифры.** Всё, что видит пользователь — название
проекта, валюта, показатели, выводы, тексты разборов, настройки агента — приходит
с бэкенда. Собранный бандл про данные клиента ничего не знает.

## Запуск

```bash
npm install
cp .env.example .env.local     # адрес бэкенда
npm run dev                    # http://localhost:5173
```

Без бэкенда экраны покажут ошибку с кнопкой повтора — это правильное поведение,
а не поломка. Чтобы работать над интерфейсом, пока бэкенда нет, поднимите демо-сервер:

```bash
npm run mock     # http://localhost:8787, вымышленные данные из mock-server/
```

В `.env.local` при этом должно стоять `VITE_API_PROXY=http://localhost:8787`.

```bash
npm run build             # tsc + vite build → dist
npm run typecheck         # только типы
npm run build:standalone  # весь кабинет одним файлом → standalone/rakurs.html
```

## Подключение бэкенда на VPS

```dotenv
VITE_API_URL=/api                        # куда фронт шлёт запросы
VITE_API_PROXY=https://api.example.com   # куда dev-сервер проксирует /api
```

Прокси нужен, чтобы фронт и апи были на одном origin и не пришлось настраивать CORS.
В продакшене то же самое делает nginx — пример конфига в `deploy/nginx.conf.example`.

Деплой:

```bash
npm run build
rsync -a --delete dist/ vps:/var/www/rakurs/
# nginx: root /var/www/rakurs, /api → 127.0.0.1:3000
```

Три вещи, на которых обычно спотыкаются:

1. **`try_files $uri $uri/ /index.html`** в nginx обязателен. Роутер живёт в браузере,
   без этой строки прямой заход на `/dialogs` или F5 внутри приложения вернут 404.
2. **Токены Meta, amoCRM и WhatsApp — только на бэкенде.** Всё с префиксом `VITE_`
   вкомпилируется в бандл и будет видно в исходниках страницы. К Marketing API и
   Conversions API ходит сервер, он же хэширует телефон и e-mail в SHA-256 перед
   отправкой события.
3. **Долгие ответы и WebSocket.** Разбор диалога моделью и синхронизация с Meta
   занимают десятки секунд, статус привязки номера по QR приходит по WebSocket —
   в примере конфига подняты `proxy_read_timeout` и заголовки `Upgrade`.

## Что должен отдавать бэкенд

Формы данных описаны типами в `src/types/index.ts`, вызовы — в `src/api/index.ts`,
рабочий пример каждого ответа — в `mock-server/`. Всё в JSON; ошибки обычными кодами
HTTP, тело вида `{"message": "..."}` показывается пользователю как есть.

| Метод и путь | Что отдаёт |
|---|---|
| `GET /api/profile` | название проекта, тариф, валюта, курс доллара, инициалы пользователя |
| `GET /api/settings` · `PATCH /api/settings` | выбранные рекламные аккаунты, режим синхронизации |
| `GET /api/ad-accounts` | рекламные аккаунты Meta Business |
| `GET /api/creatives?days=30` | объявления: расход из Meta и выручка из CRM в одной строке |
| `GET /api/ads/insights?days=30` | показатели Ads Manager по объявлениям |
| `PATCH /api/ads/:id` | включение и выключение объявления |
| `POST /api/ads/bulk` | массовые действия над выделенными строками |
| `GET /api/overview?days=30` | выводы «где теряем деньги» и показатели периода |
| `GET /api/benchmarks?days=30` | средние по отделу для сравнения в разборе объявления |
| `GET /api/capi/reconciliation?days=7` | сверка событий CRM → Ракурс → Meta и EMQ |
| `GET /api/dialogs?days=30&outcome=&creative=&q=` | диалоги с AI-разбором; фильтрует сервер |
| `POST /api/dialogs/:id/reanalyze` | пересчитать разбор одного диалога |
| `GET /api/sellers?days=30` | рейтинг продавцов и сводка по отделу |
| `GET /api/sellers/activity?days=30` | обращения и сообщения по часам и дням недели |
| `GET /api/broadcast/config` | сегменты, шаблоны, история, качество номера и лимиты |
| `POST /api/broadcast` | запуск рассылки |
| `GET /api/whatsapp/numbers` · `DELETE /api/whatsapp/numbers/:phone` | номера продавцов |
| `POST /api/whatsapp/qr` · `GET /api/whatsapp/qr/:id` · `DELETE` | привязка номера по QR |
| `GET /api/integrations` | состояние amoCRM, Instagram Direct и прочих подключений |
| `GET /api/agent` · `PATCH /api/agent` | база знаний, правила, тайминги, примеры ответов |

Правила предполётной проверки рассылки обязаны стоять и на сервере. Кнопка в интерфейсе —
удобство, а не защита: без согласия на переписку, при превышении лимита двух маркетинговых
сообщений в сутки на человека (ошибка 131049) или при залповой отправке Meta блокирует номер.

## Как устроено

```
src/
├── api/          все обращения к бэкенду: client.ts — транспорт, index.ts — вызовы
├── components/
│   ├── layout/   сайдбар, шапка, каркас экрана
│   ├── ui/       примитивы, состояния загрузки и пустоты, всплывающие сообщения
│   └── <экран>/  крупные блоки конкретных экранов
├── hooks/        useApi — загрузка с отменой и повтором
├── lib/          константы интерфейса, форматирование и склонения, цветовые тона,
│                 агрегаты, предполётная проверка рассылки, переходы с контекстом
├── screens/      по файлу на экран
├── store/        app-state — что выбрано на экранах; data — опорные данные с бэкенда
├── styles/       дизайн-токены, шрифты, общие классы
└── types/        доменные типы — контракт с бэкендом

mock-server/      демо-сервер и вымышленный набор данных. В сборку не попадает,
                  нужен только чтобы кликать интерфейс без бэкенда
```

В `src/lib/constants.ts` лежат постоянные величины интерфейса: часы тепловой карты,
дни недели, варианты темпа рассылки и окна отправки, инструкция по привязке номера,
объяснение механик защиты от бана. Это устройство продукта, одинаковое у всех клиентов,
а не их данные.

Опорные данные — профиль, аккаунты, объявления, показатели, продавцы, настройки —
грузятся один раз в `store/data.tsx` и общие для всех экранов: счётчики в меню, обзор
и таблица креативов считаются из одного набора. Перезапрашиваются при смене периода.

Пока запрос идёт, экран показывает заглушки той же высоты, что и содержимое. Если
запрос не прошёл — сообщение с кнопкой повтора. Если данных просто нет — понятная
строка вместо пустоты («За этот период оплат ещё нет»), а не нули и прочерки.

Действия, меняющие данные на сервере — тумблеры объявлений, массовые операции, выбор
аккаунтов, режим и правила агента — применяются в интерфейсе сразу, не дожидаясь ответа.
Если сервер отказал, состояние возвращается и появляется сообщение об ошибке.

## Дизайн-система

Токены объявлены CSS-переменными в `src/styles/tokens.css`: тёмная тема на `:root`,
светлая на `:root[data-theme="light"]`. Светлая — по умолчанию, выбор пишется
в `localStorage['rakurs-theme']` и читается синхронно в `index.html` до первой
отрисовки, иначе видно вспышку светлой темы.

Плоский стиль: теней нет, разделение только границами `1px`. Из анимаций — пульсация
индикаторов активности и мерцание заглушек, обе отключаются при `prefers-reduced-motion`.

Шрифты — Golos Text (интерфейс) и JetBrains Mono (числа, идентификаторы, таймстемпы) —
лежат в `public/fonts` и подключаются из `src/styles/fonts.css`. Оба под SIL Open Font
License 1.1. Локальные файлы убирают запрос к стороннему CDN, снимают мигание текста
при загрузке и делают отрисовку одинаковой в офлайне.

## Что осталось за рамками

- Мобильная версия. Экраны рассчитаны на десктоп от 1440px, у контентной области
  `min-width: 1150px`. Мобильные нужно проектировать отдельно, а не сжимать эти.
- Авторизация. Запросы уходят с `credentials: 'include'`, но экрана входа нет —
  он появится вместе с бэкендом.
- Пагинация списка диалогов: сейчас приходит весь набор за период.
